# ADR-0013: Authenticate webhooks with HMAC-SHA256 over timestamp and body

**Status**: Accepted
**Date**: 2026-10-26

## Context

A webhook delivery is an outbound HTTP request to a URL the customer supplied.
The receiver has to answer two separate questions, and they need different
mechanisms:

1. **Did this really come from us, and was the body altered in transit?** Anyone
   who knows a customer's endpoint URL can POST to it. Without a signature, the
   receiver cannot distinguish a real delivery from a forged one.
2. **Is this a fresh request, or a replayed one?** Delivery is at-least-once
   (ADR-0005), so the receiver must also tolerate genuine duplicates. It must not,
   however, accept a request captured by an attacker and re-sent later.

Endpoint URL confidentiality is not a control: URLs appear in logs, proxies,
browser history and error reports.

Each tenant has a `webhook_secret`, generated by `secrets.token_hex(32)` at
tenant creation and shown once, exactly like the API key (ADR-0012).

## Decision Drivers

- **Must** let the receiver verify integrity and origin without a shared
  session, since the receiver is a third party's server.
- **Must** make a captured request useless to an attacker later.
- **Must** be implementable by a customer in a few lines, in any language.
- **Should not** require the receiver to make a call back to us to verify.
- **Must** tolerate the receiver's clock being somewhat wrong.

## Considered Options

### Option 1: A static bearer token in a header

- **Pros**: Trivial for the receiver.
- **Cons**: Provides no body integrity — an attacker who captures the token can
  forge arbitrary payloads — and the token appears verbatim in logs and proxies.
  Does not answer question 2 at all.

### Option 2: Signature over the body only

- **Pros**: Answers question 1 properly with `HMAC(secret, body)`.
- **Cons**: Answers nothing about question 2. Any captured request can be
  replayed indefinitely, and the signature remains valid forever. This is the
  common mistake: the signature is correct, so the request looks authentic.

### Option 3: HMAC over `<timestamp>.<body>`, timestamp sent as a header

- **Pros**: Answers both questions. Because the timestamp is inside the signed
  payload, an attacker cannot refresh the timestamp without invalidating the
  signature, so a captured request stops being accepted once it falls outside the
  tolerance window. Stateless on the receiver: no nonce store.
- **Cons**: Depends on the receiver's clock, so an explicit tolerance window is
  required. Does not prevent replay *within* the window, so it narrows the attack
  rather than eliminating it.

### Option 4: Asymmetric signatures (Ed25519 / RSA), verify with a public key

- **Pros**: The receiver never holds a secret that can be used to forge
  deliveries; the public key can be published.
- **Cons**: Key distribution, rotation and format become part of the customer
  integration. Meaningfully harder for a customer to implement in an arbitrary
  language, and this is a webhook, not a signed artifact.

## Decision

We will sign each webhook with **HMAC-SHA256 over `<timestamp>.<body>`**, sending:

- `X-Webhook-Timestamp`: Unix seconds, also inside the signed payload;
- `X-Webhook-Signature`: the hex digest, with a `sha256=` prefix.

Verification is provided as `app.security.verify_signature`, which is the
implementation in the service, the test suite and the bundled demo receiver —
so all three verify the same code rather than a copy of it.

## Rationale

The decisive driver was that question 2 cannot be answered by a body signature
alone, and the common implementation of webhook signing answers only question 1.
Putting the timestamp inside the signed payload is what makes replay protection
work without state: the attacker cannot re-timestamp the request without the
secret, so the age check is trustworthy.

Symmetric HMAC was chosen over asymmetric signatures because the secret is
already part of onboarding — the customer is handed a `webhook_secret` when the
tenant is created — so no new key distribution problem is created. Asymmetric
signing would be a stronger story at the cost of a materially harder customer
integration, for a threat (forgery by the receiver itself) that is not in scope.

Comparison uses `hmac.compare_digest`, not `==`. The signature is a secret-derived
value, and a byte-by-byte early-exit comparison leaks information about it.

The tolerance window is 300 seconds because receivers commonly run with drifting
or misconfigured clocks, and a webhook that a customer cannot verify because
their clock is 90 seconds fast is worse than a five-minute replay window. The
window narrows the attack; it does not eliminate it, and that is stated plainly.

## Consequences

### Positive

- The receiver can verify origin and integrity with one HMAC and one comparison.
- A captured request expires: it is rejected once outside the tolerance window.
- Verification is stateless on the receiver — no nonce storage.
- Verified end to end with the bundled receiver: 2,000 of 2,000 webhooks
  signature-verified and accepted during the load test.
- The verification function ships with the service, so a customer can vendor or
  port it instead of guessing at the format.

### Negative

- The receiver must implement verification; nothing enforces that it does. A
  customer who ignores the headers gets an unauthenticated webhook and no warning.
- Real duplicates within the tolerance window are still accepted, and since
  delivery is at-least-once they are expected. Deduplication is by
  `X-Notification-Id`, which is sent on every delivery.
- One secret per tenant: a compromised secret affects every webhook for that
  tenant, and there is no rotation mechanism (the same gap as ADR-0012).
- Clock skew beyond the tolerance rejects legitimate deliveries, and the failure
  looks to the customer like a rejected signature rather than a clock problem.

### Risks

- **A receiver that ignores `X-Webhook-Signature`** has no protection at all.
  Out of our control; documented in the integration contract.
- **A receiver behind a body-mutating proxy** (for example, one that reorders
  JSON) would fail verification. The signature covers the exact bytes sent, which
  is correct and is why the demo receiver reads the raw body rather than a
  re-serialised object.
- **A wrong secret on the receiver side produces `401`s**, which this service
  classifies as a permanent failure (ADR-0006) and dead-letters after one
  attempt. Observed during testing, and it is the intended behaviour: a signature
  rejection will not fix itself by retrying. The cost is that a misconfigured
  receiver learns about the problem from dead-lettered notifications rather than
  from a retry storm.

## Implementation Notes

- `app/security.py`: `SIGNATURE_HEADER`, `TIMESTAMP_HEADER`,
  `DEFAULT_TOLERANCE_SECONDS = 300`, `sign_payload`, `verify_signature`.
- Signed payload format is `timestamp + "." + body`, using the raw body bytes.
- `app/channels.py` adds both headers to every webhook delivery alongside
  `X-Notification-Id`.
- `scripts/webhook_receiver.py` verifies signatures and logs
  `verified_signature` / `rejected_signature` counts, so the behaviour is
  observable in a demo.
- Covered by `tests/test_signing.py`, including signature verification and
  replay-window rejection.
