# ADR-0012: Store API key hashes with SHA-256, not a password KDF

**Status**: Accepted
**Date**: 2026-10-26

## Context

Tenants authenticate with an API key. The key must be verifiable on every
authenticated request and must not be recoverable from the database, so that a
database leak does not hand an attacker working credentials for every tenant.

The default instinct is "hash secrets with bcrypt or Argon2". Those functions
are deliberately slow and memory-hard, and they exist for one specific reason:
passwords are chosen by humans and have low entropy, so an attacker who steals
the hash can brute-force a meaningful fraction of them. The cost is deliberate
and worth paying.

API keys here are generated by `secrets.token_urlsafe(32)` — 256 bits of
cryptographic randomness. They are not guesses, are not reused across services,
and have no structure to exploit.

## Decision Drivers

- **Must** not store the key in a form that allows recovery.
- **Must** keep verification cheap enough to run on every authenticated request.
- **Must** look up by key without a table scan.
- **Should** keep the property that a stolen database does not yield usable keys.

## Considered Options

### Option 1: Store the key in plaintext

- **Pros**: Zero cost to verify; simplest possible.
- **Cons**: A database read, a backup file, or one careless log line hands over
  every tenant's credentials. Rejected outright.

### Option 2: bcrypt or Argon2, the standard password-hashing advice

- **Pros**: Familiar; resistant to brute force; per-hash salt included.
- **Cons**: 50–300 ms of deliberate work per verification, on every request.
  That is a measurable tax on the ingest path — the same path where a 218 ms
  cross-store call was treated as unacceptable (ADR-0003). And it buys nothing
  against a 256-bit random key: there is no dictionary to attack, so the slow
  hash protects against a threat that does not exist.

### Option 3: SHA-256 of the key, indexed and unique

- **Pros**: One fast hash per verification; the stored value is not reversible;
  the digest is directly indexable, so lookup is a single index probe; length is
  fixed, so the column is `VARCHAR(64)`.
- **Cons**: No per-row salt, no stretching. Identical keys produce identical
  digests (irrelevant here — a collision would require a full-entropy collision).

### Option 4: SHA-256 with a server-side pepper (HMAC)

- **Pros**: A database leak alone is not enough; the attacker also needs the
  application secret.
- **Cons**: Verification needs a server-side secret, which must be stored,
  rotated, and made available to every process. Introduces an operational secret
  whose loss locks out every tenant — a real availability risk traded against a
  modest gain, given the key is already high-entropy.

## Decision

We will store `sha256(api_key)` in a unique, indexed column, generate keys with
`secrets.token_urlsafe(32)` behind an `ntf_` prefix, and show the plaintext key
exactly once at creation.

## Rationale

The decisive driver was that a password KDF defends against low entropy, and
these keys do not have low entropy. Applying bcrypt here would pay its full cost
on the hot path to mitigate an attack that is infeasible anyway: brute-forcing a
256-bit random value is not a matter of time or hardware.

SHA-256 also permits the lookup to be an index probe. With a per-row salt (as
bcrypt uses), verification would require fetching candidate rows and comparing,
turning an indexed equality into a scan — the property that makes the fast path
fast.

Option 4 was rejected on operational grounds: introducing a pepper means every
process needs a secret whose loss is an outage, for a marginal gain over an
already-infeasible attack. The honest framing is that the *hashing choice* is not
the weak point of this design; key lifecycle is.

## Consequences

### Positive

- Verification is a single indexed hash and one lookup, with no deliberate delay
  on the ingest path.
- A stolen database yields digests, not keys. Recovery requires inverting
  SHA-256 on high-entropy inputs.
- Keys are URL-safe and prefixed (`ntf_`), so they are recognisable in logs and
  secret scanners, and cannot be mistaken for a password.
- The `ntf_` prefix also means a leaked key can be detected by scanning for the
  pattern in commit history or CI output.

### Negative

- **No key rotation or expiry.** A key lives as long as the tenant row. There is
  no `rotate-key` command, no `last_used_at`, and no revocation short of deleting
  the tenant or editing the row. This is the weakest part of the design and it is
  recorded rather than glossed over.
- No per-key audit trail: the tenant is identified, but which of a tenant's keys
  was used is not tracked, and multiple keys per tenant are not supported.
- Rotating the hash invalidates a key with no grace period, so rotation would be
  a breaking change until a two-key scheme exists.

### Risks

- **A leaked key cannot be revoked without touching the row.** Mitigated in
  practice by `UPDATE tenants SET api_key_hash = ...`, but it is not a supported
  operation and is not exposed through the CLI.
- **No rate limiting per key, only per tenant.** Since there is one key per
  tenant, these are equivalent today, and would stop being equivalent if a tenant
  had several keys.
- **Hash comparison is by index lookup, not `compare_digest`.** This does not
  leak the key: the attacker cannot control the stored value, and the query is
  for the hash of what they presented.

## Implementation Notes

- `app/security.py`: `hash_api_key`, `generate_api_key`, `API_KEY_PREFIX`.
- `app/models.py`: `Tenant.api_key_hash` is `String(64), unique=True` (SQLAlchemy
  also indexes unique columns), so verification is one index probe.
- `app/cli.py`: the plaintext key is printed once at creation and never stored;
  losing it means creating a new tenant or editing the hash directly.
- `app/routes.py`: `current_tenant` hashes the presented token, then looks up a
  **cached** `TenantAuth` (id and rate limit only) so a cache hit authenticates
  without touching Postgres. The row is not cached in full — notably not the
  webhook secret, which only the worker reads.
